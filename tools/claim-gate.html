Claim gate

Starting a first meeting? You do not need this tool, a schema, or JSON. Start with the eight questions, then record the discussion on the Claim Card or printable meeting brief.

Use the ladder as a stop rule, not a score. Start with the decision, intended use, and subject/scope, then require the weakest claim that is sufficient for that decision. Do not average strength at one claim level into another. Use the Claim Gate when a structured record or handoff is useful; it can import/export claim.json for portable use across tools.

Do not assign six statuses to one project. “Output: strong; Deliverable: almost; Operating capability: not yet; Outcome / Value: unknown” is a maturity-ladder misuse. The same project can PASS an exploration decision and be BLOCKED for a different repeated-operation decision because the intended use and scope differ.

Gate ≠ truth. A gate result evaluates the supplied scoped decision record. It is not an independent audit of the underlying system, measurement, or evidence and not a project-wide maturity status.

Decision soughtClaim that normally matters
Get access to try it?01 Access
Keep exploring?02 Output
May someone rely on it?03 Deliverable
Sell, operate, or support the named use repeatedly?04 Operating capability — ask “for what scope and boundary?”
Did the result change?05 Outcome
Scale, renew, expand, or stop?06 Value

An Access decision only justifies trying the tool. Having access never licenses relying on what it produces, operating it, or claiming an outcome; each of those needs its own decision and a higher claim.

Outcome and Value instruments

For upper-claim decisions, fill the evidence boundary separately from the gate. Completing either instrument does not mark a gate check PASS automatically.

  • Outcome worksheet — baseline/after, confounds, adverse effects, attribution, reversal rule
  • Value cost ledger — labour movement, elapsed time, full cost, alternatives, option value
  • Software Outcome pack — DORA-oriented measurement suggestions

Filled teaching records

  • Website prototype — Explore PASS
  • Same website — Operate BLOCKED
  • Internal tool — Rely PASS
  • Killed idea — Outcome PASS

Optional machine-readable contract

After or alongside the human record, the interactive UI, CLI, WebMCP, native MCP and CI can use the same versioned files:

  • claim.schema.json
  • decision-gates.json

The editable form requires JavaScript. The human decision path above does not. AI and terminal/IDE clients can evaluate the same claim.json through the native MCP server or deterministic CLI when structured handoff is useful.
